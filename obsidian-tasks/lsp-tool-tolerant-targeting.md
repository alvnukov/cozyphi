## Body

**Проблема.** Пользователь видит много ошибок тулы lsp, например: `Error: lsp: references requires symbol or line+character, not both`. Валидация в internal/tools/lsptool/lsp.go (и дублирующая в internal/lsp/manager_impl.go validateQuery) построена как жёсткая матрица «ровно один способ адресации» и отвергает то, что модель передаёт нативно: symbol вместе с line+character (модель берёт и имя, и позицию из grep-заголовка), symbol + line без character, а при вызове вообще без цели выдаёт то же вводящее в заблуждение «not both». Дополнительно: symbol-режим находит только символы, объявленные в файле (documentSymbol) — запрос по имени функции, которая в файле лишь используется, молча возвращает пустой результат; calls без direction — ошибка; symbols с file и query одновременно — ошибка.

**Что сделать.** Ослабить матрицу в пользу того, что модель ожидает: (1) symbol + позиция вместе — валидно, позиция служит уточнением: среди нескольких объявлений выбирается ближайшее к line, а если символ в файле не объявлен — резолв по позиции или по вхождению символа на указанной строке; (2) symbol без позиции, не объявленный в файле — искать первое вхождение имени в тексте файла (символу достаточно встречаться в файле, как в happ code); (3) принять квалифицированное имя Container.Name; (4) вызов без цели — честное сообщение «requires symbol or line+character» без «not both»; line без character без symbol — подсказка, чего не хватает; (5) calls: direction по умолчанию incoming; (6) symbols: file + query = символы файла, отфильтрованные по query. Обновить описание тулы и схему, чтобы модель знала о допусках; поправить оба слоя валидации и тесты.

**Критерий.** Вызов references с symbol+file+line+character возвращает результат, а не ошибку; symbol, лишь используемый в файле, резолвится по вхождению; неоднозначный символ с line выбирает ближайшее объявление; сообщения об ошибках точные; тесты на все допуски и на сохранившиеся отказы; гейт rc=0.

**Расширение (решение пользователя: полный редизайн).** Цель — чтобы модель для структурных вопросов не грепала вовсе: (а) file опционален — definition/references/hover/calls по одному symbol резолвятся через workspace/symbol (точное имя, при неоднозначности — список кандидатов, при отсутствии — ближайшие fuzzy-совпадения с предупреждением); (б) к каждой локации в результатах прикладывается сниппет строки кода (bounded), чтобы модель не дочитывала файлы после каждого ответа; (в) новые операции implementations и type_definition (gopls: textDocument/implementation, textDocument/typeDefinition); (г) описание тулы и схема переписаны под новые допуски. Критерий расширения: «где объявлен Foo» и «кто реализует интерфейс X» отвечаются одним вызовом без file и без грепа, результаты со сниппетами; гейт rc=0.

**Результат.** Полный редизайн выполнен, коммит 95b52d3 на feature/lsp-tolerant-targeting, мерж в main 8fea80b. (1) Толерантный таргетинг для всех навигационных операций (definition/references/implementations/type_definition/hover/calls): symbol, line+character или любая комбинация; позиция при нескольких объявлениях одного имени выбирает ближайшее по selection-строке; принимается квалификация Container.Name; символ, лишь используемый в файле, резолвится по вхождению (identifier-bounded скан: сначала подсказка line, затем первое вхождение), отсутствующее имя отвечает предупреждением, а не пустотой. (2) file опционален при symbol: имя резолвится через workspace/symbol до выбора Go-root; единственное совпадение продолжает запрос прозрачно, неоднозначное отвечает списком квалифицированных кандидатов (для definition — локациями объявлений), промах — ближайшими символами workspace с предупреждением. (3) Каждая локация несёт сниппет строки кода (прикладывается после дедупликации, в идентичность не входит; те же сниппеты у call-site'ов). (4) Новые операции implementations и type_definition на общем location-lookup, терпимом к результатам вне workspace (считает и сообщает omitted). (5) calls: direction по умолчанию incoming; symbols: file+query = отфильтрованный outline. (6) Описание тулы и схема переписаны; обе матрицы валидации (lsptool build и manager validateQuery) симметрично ослаблены, каждое оставшееся сообщение об ошибке называет ровно недостающее — «not both» исчез. Тесты: internal/lsp/targeting_test.go (nearest-declaration, полная позиция, occurrence-fallback, absent-symbol warning, Container.Name, workspace-резолв/неоднозначность/промах, implementations e2e со сниппетом, type_definition одиночный объект, definition со сниппетом, symbols file+query, validateQuery-матрица, occurrenceColumn) плюс перепиленные TestBuildValidationMatrix/TestBuildTolerantTargeting/рендер-тесты в lsptool. Гейт make fmt-check lint test rc=0 на ветке; make test на main после мержа rc=0. Границу честно фиксирует описание тулы: строковые литералы, комментарии, regex и не-Go файлы остаются текстовому поиску.
